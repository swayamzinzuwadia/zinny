Zinny stops being one product sold one way.

It becomes one management platform that an institute can enter three ways: under its own brand, through its own website, or through Zinny's marketplace. The direct way is the main one. These are the calls already made.

Direct institutes

The institute keeps its own website, its own login and its own payment gateway. Every sign-up and purchase flows into Zinny, and the institute is run from Zinny.

Where their students learn

In Zinny's own portal and app, showing the institute's name and logo inside a Zinny frame.

White label

Two price tiers. Standard runs on the shared platform. Premium is a dedicated installation with its own database.

Marketplace money

Zinny collects the payment, keeps a commission and pays the institute the rest.

Sellers with no subscription

A seller console only: recorded courses, listings, codes, buyers, sales and payouts. Batches, tests and student management come with a subscription.

Live classes

A built-in classroom inside the product, charged by use. Pasted Meet or Zoom links stay as a fallback.

Mobile apps

Phase 2, for Android and iOS. A white-label institute can buy its own app in the stores, built from the same code.

The code

Today's repository is evolved. Nothing that works is rewritten.

Eight changes underneath carry everything else.

They are built first, by one agent working alone, before any parallel work starts. A separate review checked each one against the code.

Changes one to four

Who the visitor is, where their account lives, and how data comes in.

The web address decides the site

A new list of addresses per institute. When a request arrives, Zinny looks up the address and shows that institute's pages under its own short links.

The 165 existing pages are not moved. Old links keep working and redirect once.

Accounts live in sets

Zinny has one set of accounts. Each white-label institute has its own private set, so the same email can exist in both with no clash and no hint.

A person signed in at one white-label institute can never reach another.

A student record per institute

Separate from the login: student ID, contact details as the institute holds them, where the student came from, status and custom fields.

Orders record where they came from, and can be marked as paid outside Zinny.

A front door for outside systems

Keys per institute, one address for all API calls, and a place where each module adds its own endpoints.

Messages back to the institute's site are queued and retried, never sent in the middle of saving.

Eight changes underneath, continued.

Money, brand, plans and the door for mobile.

Changes five to eight

Where the money goes, whose name shows, and what each plan allows.

Money per institute

Today one gateway serves everyone. It becomes a gateway chosen per institute and per purpose, with keys stored encrypted.

The gateway can split one payment between sellers, which the marketplace needs.

One source for the brand

One function answers: whose name, logo, colours, sender and legal links apply here. Colours switch per institute without touching any page.

An automatic check fails the build if the word Zinny appears where an institute's people would see it.

Plans that are enforced

Each institute's plan says which sections are on and how many students and staff it may have. The menu, the pages and the add-person paths all read it.

An API the apps can use

The same business rules, reachable with a token instead of a browser cookie, plus a device list for push messages.

Started now so the mobile apps have something to talk to.

Repairs come before any of this. The build rules and the code have drifted apart: modules import each other, the ownership check cannot run, only the daily job is scheduled, and the guide names the wrong framework version. These are fixed first so that agents can work in parallel safely.

Live classes happen inside Zinny.

Today a teacher pastes a meeting link and Zinny only records who clicked Join. The class moves in.

The classroom

Each class on the timetable gets its own room.

  • Video, audio, screen share, whiteboard
  • Share a PDF or slides; moderated chat; raise hand; quick polls
  • Waiting room, mute all, remove, co-teacher
  • A weak-network mode and a connection test
  • A watch-only mode for very large batches

What it does for the institute

The work after class disappears.

  • Attendance from real presence, which staff can correct
  • Recordings saved and attached to the class
  • Published as a lesson automatically, if the batch says so
  • Minutes counted per institute and billed as an add-on
  • Pasted links still work as a fallback

Recorded video grows up too

Uploads

Go straight to storage in parts that resume, replacing today's slow relay through the app.

Playback

Converted for smooth streaming at several qualities. Links are signed and expire.

Protection

The viewer's name floats over the video to deter screen recording, with stronger copy protection on higher plans.

Library

Captions, playback speed, a shared content library reused across courses, and storage counted per institute.

The video service sits behind one interface so it can be swapped. It is chosen after a one-week trial of three services on cost per minute, quality on Indian mobile networks, recording and mobile support.

Each Claude Code feature has one job here.

The features are tools for the cycle on the previous page, not a goal in themselves.

Plan mode

Before every stage and before each agent builds. Read and propose first, change nothing.

Agent briefs

One file per agent with its model, its effort level and its instructions. The team is written down, not improvised.

Separate working copies

Each builder gets its own copy of the code, so no two agents touch the same files.

Cloud sessions in parallel

One session and branch per wave agent. Each opens a pull request and fixes its own failing checks and review comments.

Workflows

Scripted runs of many agents with a verify step: the wording sweep, and the review pass on every branch of a wave. Started only when you ask.

Search and design agents

A read-only searcher and an architect, built in. They answer questions without filling the lead's memory.

Skills

Reusable know-how: card-to-page motion, code review, security review, running the app, and four new ones written in the foundation stage.

Hooks

Automatic rules: refuse an edit outside the agent's folders, run the ownership check before an agent stops, set up the database when a session starts.

Scheduled tasks

Every night, the full test run and the Zinny-wording count on the merged branch. Every week, a dependency and security scan.

Shared memory

The project guide and the handoff notes carry knowledge between agents and between sessions.

Connecting a direct institute's site, step by step.

The Zinny team follows this for every institute, starting with the first pilot. The Integration desk tracks it.

1

Discovery call

How the site is built, which gateway it uses, what it collects at sign-up, how products are named, whether a developer is available.

2

Create the institute

On the Direct plan, and invite its admin.

3

Set up the catalogue

Departments, courses, batches, fees, student ID format.

4

Pick the connection

Plugin for WordPress, API for a custom site, gateway listener when there is no developer.

5

Issue test keys

The site sends test sign-ups and orders. Check them in the sync monitor.

6

Map products

To courses and batches, and set the placement rules.

7

Add the button

Go to my classes, on the site's account page. Test the handoff.

8

Load existing students

A CSV with the site's IDs, so earlier students match later orders.

9

Reconcile one week

Counts on the site against counts in Zinny.

10

Go live

Switch to live keys, watch the first real orders, hand Arrivals to the institute's staff.

11

After launch

Weekly reconciliation for a month, then alerts only.

What could go wrong, and what the plan does about it.

Sign-in breaks for everyone

The account change is done alone in the foundation stage, behind every existing test plus new separation tests.

Integrations drag on

Three connection types from day one, an option for sites with no developer, a test institute, and the step-by-step playbook.

A site sends wrong or duplicate data

Writes that can be repeated safely, the site's own IDs as the key, a duplicates list, reconciliation and replay.

Marketplace tax is misjudged

The accountant's and the gateway's sign-offs are gates for that stage.

The Zinny name leaks into a white label

One brand source, a build check on stray wording, and a screenshot sweep of every surface under a test brand.

Video costs outrun income

Minutes and storage are counted from the first day and sold as add-ons, with limits per plan.

Dedicated installations multiply work

Same code, set by configuration, updated on a schedule after the shared platform, and built last.

The apps stall on missing server features

The app API and token sign-in start in the foundation stage.

Agents collide

Ownership and contracts are repaired first; one agent per module; an integrator merges each wave.

How each stage proves it is done.

Every stage also passes the type check, lint, all tests and the ownership check, and saves screenshots.

1A Foundation

All existing tests pass. A test brand at a second address shows no Zinny name at sign-in. Two accounts with the same email in different sets sign in separately. A call with a key reads a course list.

1B Direct

A sample WordPress site sends a sign-up and a paid order; the student appears in Arrivals with an ID; the handoff link signs them in to that institute only; replaying the order changes nothing.

1C White label

A browser sweep of every surface under a test brand fails on the word Zinny. A checkout is paid through a test gateway account that belongs to the institute.

1D Marketplace

A seller-only institute signs up and lists a course; a buyer pays in test mode; the ledger shows the split; a refund reverses it; the daily match balances.

1E Classroom

Two browsers join a class, attendance is recorded from presence, and the recording appears as a lesson.

1F Billing

An institute pays a Zinny invoice in test mode. A section outside the plan is hidden and refused. Adding a student over the cap is blocked after the grace period.

1I Launch

A load test on the API and sign-in, an outside security test, and a dry run of moving today's institutes.

Phase 2

The same flows on a low-end Android phone and an iPhone, with offline and push, then beta through the stores' test channels.
